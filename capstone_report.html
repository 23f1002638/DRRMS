Abstract

Disaster relief operations are inherently chaotic, demanding rapid coordination among administrators, volunteers, victims, and donors. Existing ad hoc mechanisms â€” fragmented phone logs, paper registers, and siloed spreadsheets â€” routinely fail under the stress of large-scale emergencies, producing duplicated efforts, overlooked aid requests, and inequitable resource allocation.

This project presents the Disaster Relief and Resource Management System (DRRMS), a comprehensive full-stack web application that digitalises and centralises the entire relief lifecycle. The system implements a strict Role-Based Access Control (RBAC) model serving four user classes: Administrators access live KPI dashboards and inventory controls; Volunteers browse, claim, and complete aid tasks; Victims submit geo-tagged SOS requests and monitor their status; and Donors log contributions and view impact metrics.

The backend is an Express.js REST API backed by an SQLite relational database, secured via JWT authentication and bcryptjs password hashing. The frontend is built with React 18, TypeScript, and Vite, styled with Tailwind CSS and accessible Radix UI components. Key features include a polling-based real-time data layer implemented through custom React hooks, geolocation-based nearest-resource discovery using the Haversine formula, analytical charts via Recharts, an interactive map using React-Leaflet with OpenStreetMap tiles, and an embedded rule-based AI chatbot for intent-driven guidance.

The system was validated through structured unit and integration testing, achieving complete coverage of all primary user workflows across all four roles. DRRMS demonstrates that a lightweight, locally deployable technology stack can deliver a production-quality platform that meaningfully improves the speed and equity of disaster relief operations.

Keywords: Disaster Relief, Resource Management, Role-Based Access Control, React, Express.js, SQLite, Geolocation, Haversine Formula, JWT, Full-Stack Web Application.

Chapter 1: Introduction

Note: Problem identification and system design were completed as part of the prior Study Project submission. This chapter incorporates and extends that work.

1.1 Overview of the Project

The Disaster Relief and Resource Management System (DRRMS) is a full-stack, role-based web application that streamlines and centralises disaster relief coordination across four stakeholder groups: Administrators, Volunteers, Victims, and Donors. Critical relief activities â€” aid request dispatch, inventory management, volunteer task assignment, geolocation-based resource discovery, and donation tracking â€” are unified within a single digital platform accessible through any modern web browser.

The platform is engineered with operational resilience as a first principle. By relying entirely on a locally deployable stack (React front-end, Express.js back-end, SQLite database), DRRMS can be set up rapidly in environments with limited or unstable internet infrastructure, making it viable during acute disaster scenarios where cloud services may be degraded.

1.2 Problem Statement and Motivation

Natural and man-made disasters place extraordinary demands on relief organisations. The effectiveness of any response correlates directly with the speed at which resources reach those who need them most. Existing coordination mechanisms suffer from several critical deficiencies:

  • Fragmentation: Aid requests arrive through multiple channels â€” phone calls, social media, and in-person reports â€” making it impossible to maintain a single authoritative list of active needs.
  • Volunteer Miscoordination: Without a central task management layer, volunteers duplicate effort on some requests while others go entirely unattended.
  • Resource Opacity: Administrators lack real-time visibility into inventory levels, producing both stockouts of critical supplies and wasteful overstocking.
  • Donor Disconnect: Donors receive no feedback on how contributions are utilised, eroding long-term trust and engagement.
  • Geographic Barriers: Victims are often unaware of the nearest available shelter, and field teams lack a geographic overview of concurrent active incidents.

DRRMS addresses each of these failure modes through technology-driven, role-aware coordination within a single integrated system.

1.3 Objectives

  1. Design and implement a secure, role-based authentication system supporting four user roles.
  2. Develop a real-time aid request management pipeline covering the full status lifecycle from submission to resolution.
  3. Build an inventory management module with low-stock alerting and restock operations.
  4. Integrate HTML5 geolocation with the Haversine formula for distance-aware resource discovery.
  5. Construct interactive analytics dashboards using Recharts for Administrators and Donors.
  6. Embed a rule-based AI assistant capable of intent-driven navigation and emergency guidance.
  7. Validate all modules through structured testing and ensure deployability both locally and on a cloud platform (Vercel).

1.4 Scope of Implementation

The implementation covers full-cycle design, development, testing, and deployment of the DRRMS web application and includes:

  • A React 18 + TypeScript SPA, bundled via Vite and served on a local dev server (port 5173).
  • A Node.js / Express.js RESTful API server exposing ten domain-specific route groups (port 3001).
  • A relational SQLite database with seven core tables enforcing referential integrity through foreign-key constraints.
  • Role-specific dashboards and shared view components for all four user roles.
  • An interactive map using React-Leaflet with OpenStreetMap tile layers and real-time marker updates.
  • A stateless JWT-based session management system with bcryptjs password hashing.

Items explicitly outside the scope of this submission include native mobile applications, live WebSocket connections, third-party logistics integrations, and multi-language localisation, all identified as potential future enhancements in Chapter 6.

2.1 System Architecture and Design

High-Level Architecture

DRRMS follows a classic three-tier client-server architecture. The presentation tier is a React 18 Single Page Application served by Vite. The application tier is a Node.js / Express.js REST API server. The data tier is a serverless SQLite database stored as a single file (database.sqlite) on the server host. All communication between the frontend and backend occurs over HTTP using JSON payloads, with every protected endpoint validated by the authenticateToken JWT middleware.

Figure 2.1 â€” High-Level System Architecture

Data Flow Diagram â€” Aid Request Lifecycle

The primary data flow illustrates how a victim's SOS request travels through the system:

  1. The Victim submits a form in AidRequestForm.tsx, which fires a POST /api/requests call.
  2. The Express server validates the JWT, inserts a new row into the aid_requests table with status pending, and returns the new request ID.
  3. Volunteer dashboards polling GET /api/requests every 5 seconds detect the new request and surface it as an available task.
  4. A Volunteer claims the task via POST /api/tasks/claim; the server atomically updates aid_requests.status to in_progress and inserts a row in volunteer_tasks.
  5. Upon completion, the Volunteer marks the task done; the server sets status to resolved and records a timestamp.
  6. The Admin dashboard and Victim's AidStatusView reflect the resolved state on the next polling cycle.

Component Interaction

The frontend orchestration layer is App.tsx, which reads the user.role claim from the decoded JWT and conditionally renders one of the four role dashboards. Shared view components (MapView, InventoryManagement, AnalyticsView, etc.) are mounted by the active dashboard based on the navigation state. All API calls are centralised in src/lib/api.ts, which attaches the Authorization: Bearer <token> header to every request automatically.

2.3 System Modules

The application is decomposed into twelve discrete modules, each encapsulating a specific business domain.

Figure 2.3 â€” Role-Based Dashboard Routing (App.tsx â†’ Role Dashboard â†’ Shared Views)

Module 1: Authentication and Authorisation

Implemented across AuthSystem.tsx (frontend) and /api/auth routes (backend). Users register with an email, password, and role. Passwords are hashed with bcryptjs (cost factor 10) before storage. On login, the server verifies the hash and issues a signed JWT encoding the user's id and role. The token is stored in localStorage and attached to every subsequent API request. A dedicated GET /api/auth/me endpoint restores session state on browser reload.

Module 2: Role-Based Dashboards

App.tsx decodes the JWT on load and conditionally mounts one of four dashboard components. Each dashboard presents only the views and actions relevant to its role, enforcing information security at the component level in addition to the API middleware level.

  • AdminDashboard: Live KPI cards (active requests, resolution rate, volunteer count), quick-action routing, system-wide notifications, and links to all management views.
  • VolunteerDashboard: Feed of available aid tasks sortable by urgency and distance; "My Tasks" panel tracking claimed assignments through to completion.
  • VictimDashboard: Prominent "Request Aid" call-to-action; GPS auto-fill on the request form; real-time status tracking of existing submissions.
  • DonorDashboard: Donation history, estimated people-helped metric, relief project overview, and contribution breakdown charts.

Module 3: Aid Request Management

Victims submit requests via AidRequestForm.tsx specifying category (food, medical, shelter, emergency), urgency (1â€“5), number of people affected, GPS coordinates, and a free-text description. Requests transition through the lifecycle: pending â†’ in_progress â†’ resolved | cancelled. AidStatusView.tsx polls GET /api/requests every 15 seconds to reflect current status without requiring a page refresh.

Module 4: Inventory Management

Administrators manage warehouse stock via InventoryManagement.tsx. Each item record carries a min_threshold; items whose quantity falls below this automatically receive a low_stock status badge and surface in the Admin dashboard alert panel. The module supports full CRUD, category and status filtering, and text search by item name or location.

Module 5: Map View and Geolocation

MapView.tsx renders a React-Leaflet map with OpenStreetMap tiles, plotting active aid requests, volunteers, and resource POIs as distinct marker types. On load, the browser's HTML5 Geolocation API is invoked to obtain the user's coordinates. geolocation.ts then applies the Haversine formula to rank every nearby resource by ground distance, populating the "Nearest Resources" sidebar.

Module 6: Analytics View

AnalyticsView.tsx consumes the GET /api/analytics aggregation endpoint, which returns pre-computed metrics from the database. The view renders: a donation trend AreaChart, an aid-request category distribution PieChart, and a volunteer task-status BarChart, all powered by Recharts with responsive container wrappers.

Module 7: Volunteer Management

Administrators access a full volunteer directory in VolunteerManagement.tsx, showing each volunteer's availability, skill tags, and aggregated task statistics (assigned vs completed, computed via SQL COUNT(CASE WHEN ...)). Volunteers interact with AvailableTasksView and MyTasksView to claim and progress tasks. A voluntary POST /api/tasks/unclaim route releases a task back to pending if a volunteer cannot complete it.

Modules 8â€“12: Donations, Resources, Support Groups, AI Assistant, Notifications

The Donations module (DonationsView.tsx) records monetary and in-kind donations and computes a people-helped estimate using the formula: floor(totalAmount / 50) + (suppliesCount Ã— 5). The Resources module lists shelters and distribution centres sortable by Haversine distance. Support Groups provides a community connection layer for grief and trauma groups. The AI Assistant (AIAssistant.tsx) is a floating chatbot widget employing keyword-scored intent matching against a curated knowledge base in ai-knowledge.ts; it can trigger in-app navigation and emergency call actions. The Notifications module polls GET /api/notifications every 10 seconds, displaying an unread-count badge on the header bell icon.

2.4 Key Algorithms and Logic

Algorithm 1: Haversine Distance Calculation

Used to compute the great-circle distance between two geographic coordinates, enabling nearest-resource ranking without an external routing API.

FUNCTION haversine(lat1, lon1, lat2, lon2):
  R = 6371  // Earth radius in kilometres
  dLat = toRadians(lat2 - lat1)
  dLon = toRadians(lon2 - lon1)
  a = sin(dLat/2)^2 + cos(toRadians(lat1))
        * cos(toRadians(lat2)) * sin(dLon/2)^2
  c = 2 * atan2(sqrt(a), sqrt(1 - a))
  RETURN R * c  // Distance in km

Algorithm 2: AI Intent Matching Engine

The chatbot parses user input through a scoring loop against a knowledge base array.

FUNCTION matchIntent(userInput, knowledgeBase):
  bestScore = 0
  bestMatch = null
  FOR EACH entry IN knowledgeBase:
    score = 0
    FOR EACH keyword IN entry.keywords:
      IF userInput CONTAINS keyword:
        score += entry.weight[keyword]
    IF score > bestScore:
      bestScore = score
      bestMatch = entry
  IF bestScore > THRESHOLD:
    RETURN bestMatch.response + bestMatch.actions
  ELSE:
    RETURN defaultResponse

Algorithm 3: JWT Authentication Middleware

FUNCTION authenticateToken(req, res, next):
  token = req.headers.authorization?.split(" ")[1]
  IF token IS NULL:
    RETURN res.status(401).send("Unauthorised")
  TRY:
    decoded = jwt.verify(token, JWT_SECRET)
    req.user = decoded          // { id, role }
    next()
  CATCH error:
    RETURN res.status(403).send("Forbidden")

Algorithm 4: Polling-Based Real-Time Data Layer

Custom hooks simulate real-time updates without WebSocket overhead.

FUNCTION useLiveRequests():
  [requests, setRequests] = useState([])
  [loading, setLoading]   = useState(true)

  FUNCTION fetchRequests():
    data = await GET("/api/requests")
    setRequests(data)
    setLoading(false)

  useEffect:
    fetchRequests()             // initial fetch
    interval = setInterval(fetchRequests, 5000)
    RETURN () => clearInterval(interval)  // cleanup

  RETURN { requests, loading }

Chapter 3: Testing, Validation and Results

3.1 Test Plan

Testing Strategy

A two-phase testing strategy was adopted. The first phase comprised unit testing of individual backend API endpoints using HTTP client tools, verifying correct status codes, response schemas, and error handling for both valid and invalid inputs. The second phase comprised integration testing of end-to-end user workflows, exercising the complete stack from the React frontend through the Express API to the SQLite database.

All four role-specific workflows were tested in full: the Admin management workflow, the Volunteer task lifecycle, the Victim aid request workflow, and the Donor contribution workflow. Additionally, cross-cutting concerns were tested independently: JWT authentication enforcement, role-based access control at the API level, and geolocation distance computation accuracy.

Tools Used

  • Browser Developer Tools (Chrome): Network tab used for manual inspection of API requests and responses during integration testing; Console for JavaScript error monitoring.
  • REST Client (Postman / Thunder Client): Used for isolated unit-level API endpoint testing, allowing header injection, body customisation, and response assertion.
  • SQLite browser: Used to directly inspect database state after operations, confirming correct data persistence and relationship integrity.
  • Haversine Manual Calculator: Used to cross-validate geolocation distance results returned by geolocation.ts against known coordinate pairs.

3.3 Results and Analysis

Observations

All 18 defined test cases passed successfully. The following observations were recorded during the testing phase:

  • Concurrency handling (TC-09) was the most critical test. The SQLite database's file-level locking combined with Express's single-threaded Node.js event loop ensured that the second simultaneous claim request was correctly rejected, preventing duplicate task assignment. No race condition was observed across 20 repetitions of the test.
  • Polling latency was observed to be within the expected 5-second window for the aid request feed and 10-second window for notifications, producing a satisfactory near-real-time experience without WebSocket complexity.
  • Haversine accuracy (TC-13) returned a distance of 1,148 km for the Delhiâ€“Mumbai coordinate pair (ground truth: approximately 1,153 km), yielding an error margin of 0.43%, well within acceptable limits for emergency resource routing.
  • JWT expiry (TC-06) correctly returns HTTP 403 at the API level; the frontend's api.ts interceptor catches 401/403 responses and clears localStorage, redirecting the user to the login screen seamlessly.
  • Low-stock alerting (TC-12) accurately propagates within one polling cycle, maintaining inventory visibility for the Admin without manual refresh.

6.1 Summary of Implementation

This capstone project designed and delivered DRRMS, a complete full-stack web application for coordinating disaster relief operations. The system was built from the ground up as a role-based platform spanning four distinct user classes â€” Administrators, Volunteers, Victims, and Donors â€” with each class provided a purpose-built dashboard and a tailored set of operational capabilities.

The implementation covered a React 18 TypeScript frontend served by Vite, a Node.js / Express.js REST API backend, and a self-bootstrapping SQLite relational database encompassing seven core tables. All primary modules â€” authentication, aid request management, volunteer task assignment, inventory tracking, geolocation-based resource discovery, analytical dashboards, donation management, an AI assistant chatbot, and a polling-based notification system â€” were implemented, integrated, and tested within the project timeline.

6.2 Achievements

  • Complete RBAC Implementation: All four user roles operate within fully isolated dashboards, with access control enforced at both the frontend routing layer and the backend API middleware layer.
  • Offline-Capable Architecture: The SQLite-based backend requires no external database server, enabling full system deployment in environments with limited infrastructure.
  • Real-Time Coordination Without WebSockets: The custom hook polling strategy delivers near-real-time data synchronisation across all dashboards with a latency of 5â€“10 seconds, without the complexity of a persistent socket server.
  • Geolocation Intelligence: The Haversine-based distance engine provides accurate nearest-resource routing to within a 0.43% error margin, enabling rapid victim-to-shelter matching.
  • 100% Test Case Pass Rate: All 18 structured test cases across unit and integration testing phases passed successfully, including the critical concurrency conflict detection test.
  • Production Deployment: The application was successfully deployed to Vercel, demonstrating cloud readiness of the frontend build pipeline.

6.3 Limitations

  • SQLite Scalability: SQLite's file-level locking is suitable for low-to-medium concurrency but would become a bottleneck under high simultaneous write loads in a large-scale deployment. A production environment with thousands of concurrent users would require migration to PostgreSQL.
  • Polling vs. WebSockets: The 5â€“10 second polling cycle introduces latency during genuine emergencies. True real-time updates (sub-second) would require a WebSocket or Server-Sent Events implementation.
  • AI Assistant Scope: The current rule-based intent matching is limited to pre-defined keywords. It cannot handle novel phrasings, multi-turn conversations, or language variations, limiting its utility for non-technical users.
  • No Mobile Application: The system is browser-based and responsive but is not a native mobile app. Victims in the field often rely on smartphones; a React Native or PWA implementation would expand accessibility.
  • Single-Server Deployment: The Express server is a single point of failure. A production deployment would require containerisation (Docker) and orchestration (Kubernetes) for high availability.

6.4 Future Enhancements

  • WebSocket Integration: Replace the polling strategy with Socket.io for true sub-second real-time updates across all dashboards.
  • PostgreSQL Migration: Migrate the data layer to PostgreSQL to support high-concurrency production deployments, leveraging row-level locking and connection pooling.
  • Large Language Model Chatbot: Replace the rule-based AI assistant with an LLM-backed conversational agent (e.g., Google Gemini API) capable of open-ended natural language understanding.
  • Progressive Web Application (PWA): Add a service worker and web app manifest to allow the application to be installed on mobile devices and used offline â€” critical for disaster zone connectivity gaps.
  • SMS / Push Notification Gateway: Integrate Twilio or Firebase Cloud Messaging to deliver critical alerts to victims and volunteers beyond the in-app notification system.
  • Multi-Language Support: Add localisation (i18n) to serve non-English-speaking victim populations, particularly important in geographically diverse disaster scenarios.
  • Automated Testing Suite: Introduce Vitest (unit tests) and Playwright (end-to-end browser tests) to automate regression detection on future code changes.

A. User Manual

For Victims

  1. Navigate to the application URL and click Register.
  2. Enter your email, a secure password, and select role Victim.
  3. After login, click Request Aid on your dashboard.
  4. Allow the browser to access your location when prompted (auto-fills GPS coordinates).
  5. Select the type of aid required, set urgency (1=low, 5=critical), enter people count, and submit.
  6. Monitor the status of your request from the Aid Status panel. Status updates every 15 seconds.

For Volunteers

  1. Register with role Volunteer and log in.
  2. Browse available tasks on your dashboard, sorted by urgency.
  3. Click Claim on a task to accept it. The task moves to "My Tasks."
  4. Travel to the location and render aid. Click Mark Complete when finished.

For Administrators

  1. Register with role Admin and log in.
  2. Monitor the KPI dashboard for live metrics on active requests and resolution rates.
  3. Navigate to Inventory to manage stock; items below threshold are highlighted in red.
  4. Use Volunteer Management to view the volunteer directory and task progress.
  5. Use Analytics to view trend charts and distribution reports.

For Donors

  1. Register with role Donor and log in.
  2. Click Make a Donation, enter the amount and category, and submit.
  3. View your contribution history and the estimated number of people helped on your dashboard.
